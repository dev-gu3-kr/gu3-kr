# Onsoa UI Harness

## 먼저 확인하기

1. 저장소가 `onsoa-nextjs`인지 확인한다. 다른 프로젝트라면 그 프로젝트의 규칙을 우선한다.
2. `AGENTS.md`를 읽고, Next.js 코드를 쓰기 전에 작업과 관련된 `node_modules/next/dist/docs/` 문서를 읽는다.
3. `components.json`, `src/app/globals.css`, 변경 화면, 인접 화면, `src/components/ui`의 기존 primitive를 확인한다.
4. 사용자가 준 참조 이미지나 기존 제품 문법이 있으면 그것을 가장 높은 시각 기준으로 삼는다.

## 구현 원칙

- `src/components/ui`와 기존 feature 컴포넌트를 먼저 재사용한다. shadcn 컴포넌트가 필요하면 설치된 shadcn 스킬을 사용한다.
- 색상, 테두리, radius, 그림자는 `globals.css`의 의미 기반 토큰을 우선한다. 장식 이미지나 도메인 시각화가 아닌 일반 UI에 임의 hex/rgb를 추가하지 않는다.
- `@/features/<feature>/{client,components,server,isomorphic}` 배럴을 통해 import하고 feature 내부 deep import를 만들지 않는다.
- Server Component를 기본값으로 두고 상호작용, 상태, 브라우저 API가 필요한 가장 작은 경계만 Client Component로 만든다.
- 모바일 우선으로 작성하되 데스크톱을 단순 확대판으로 만들지 않는다. 정보 밀도, 탐색 위치, 표·차트·다이얼로그의 표현 방식을 화면 크기에 맞춘다.
- 긴 한국어 문구, 긴 이름, 0건과 많은 건수, 누락 이미지, 느린 응답에서도 레이아웃이 무너지지 않게 한다.
- 로딩, 빈 상태, 오류, 성공, disabled/pending 상태를 실제 흐름에 맞게 명시한다.
- 키보드 포커스, label/accessible name, 명도 대비, reduced motion을 확인한다. 모바일의 주요 조작 대상은 가능한 한 44px 내외의 터치 영역을 확보한다. compact primitive를 그대로 쓸 때는 충분한 간격과 오조작 위험까지 확인한다.
- 차트와 색상만으로 전달되는 정보에는 제목, 요약, 표 또는 screen-reader용 텍스트 같은 동등한 설명을 제공한다.
- 새 UI나 큰 리디자인이면 설치된 프런트엔드 빌더 스킬의 시각 설계 절차를 함께 사용한다.

## 디바이스 검증 루프

렌더링 확인이 가능한 작업은 코드 검사만으로 끝내지 않는다. 설치된 인앱 브라우저를 우선 사용하고, 사용할 수 없을 때 Playwright를 사용한다.

1. 변경 전 기준 화면을 필요한 경우 캡처한다.
2. 최소 다음 세 뷰포트에서 변경 화면을 연다.
   - 모바일: 375×812
   - 태블릿: 768×1024
   - 데스크톱: 1440×900
3. 각 뷰포트에서 가로 스크롤, 잘림, 겹침, 과도한 빈 공간, 고정 요소 충돌을 확인한다.
4. 핵심 흐름을 클릭·키보드로 실행하고 hover/focus/open/pending/error 상태를 확인한다.
5. 콘솔 오류와 실패한 네트워크 요청을 확인한다.
6. 스크린샷을 비교해 발견한 문제를 수정하고 같은 뷰포트에서 다시 확인한다.

보호된 화면은 기존에 로그인된 인앱 브라우저 세션이나 사용자가 제공한 안전한 로컬 fixture를 우선한다. 인증을 우회하거나 자격 증명을 새로 만들지 않는다. 인증이나 데이터가 없어 특정 상태를 열 수 없으면 가능한 상태까지 검증하고, 검증하지 못한 상태와 이유를 결과에 명시한다.

## 테스트와 마무리

- 동작 로직이 바뀌면 가장 가까운 기존 Vitest 패턴으로 회귀 테스트를 추가하거나 갱신한다.
- async Server Component는 현재 Vitest로 직접 검증하기 어렵다는 Next.js 문서를 고려해, 순수 로직을 분리해 단위 테스트하거나 렌더링/E2E 검증을 선택한다.
- 파일을 변경했다면 관련 테스트를 먼저 실행하고 마지막에 `npm run verify`를 실행한다. 읽기 전용 리뷰라면 변경 영역의 기존 검증 결과를 확인하거나 필요한 최소 검사만 실행한다.
- 결과에는 변경 파일, 세 뷰포트의 확인 결과, 상태·접근성 확인, 실행한 테스트, 남은 미검증 항목만 간결하게 보고한다.
