# Onsoa Quality Loop

## 시작 조건

1. `git status --short`로 사용자 변경을 확인하고 관련 없는 수정은 건드리지 않는다.
2. `AGENTS.md`, `package.json`, 변경 영역의 기존 테스트를 읽는다.
3. Next.js 동작을 바꿀 때는 관련 `node_modules/next/dist/docs/` 문서를 먼저 읽는다.

## 작업 루프

1. 관찰 가능한 증상 또는 완료 조건을 한 문장으로 고정한다.
2. 가능한 가장 작은 재현을 만든다. 버그라면 수정 전에 재현되는지 확인한다.
3. 원인 가설을 하나씩 세우고 로그, assertion, 좁은 테스트로 반증한다.
4. 가장 싼 테스트 층을 선택한다.
   - 순수 함수, 권한, 변환, service 로직: Vitest 단위 테스트
   - route/action 계약과 데이터 경계: 직접 호출 가능한 로직을 분리한 통합 테스트
   - async Server Component와 실제 탐색·반응형 상호작용: 브라우저 또는 이미 구성된 E2E
5. 실패하는 회귀 테스트를 먼저 확인하고 최소 변경으로 통과시킨다.
6. 관측용 임시 코드와 불필요한 디버그 로그를 제거한다.
7. 관련 테스트를 다시 실행한 뒤 전체 게이트를 실행한다.

```bash
npm run verify
```

`verify`는 현재 저장소에서 typecheck, Biome, 전체 Vitest를 실행한다. 실패하면 최초 원인부터 분류한다.

- 타입 오류: nullable/직렬화/서버-클라이언트 경계와 반환 타입을 먼저 확인한다.
- Biome 오류: feature deep import와 포맷 문제를 구분한다. 자동 수정 전에 변경 범위를 확인한다.
- 테스트 오류: 제품 회귀, 잘못된 기대값, 환경 문제, 기존 실패를 증거로 구분한다.

## 디버깅 원칙

- 재현과 근거 없는 추측성 수정은 하지 않는다.
- 한 번에 한 가설만 검증하고 리팩터링은 원인 수정과 분리한다.
- 간헐적 문제는 시간, 순서, 네트워크, 캐시, 공유 상태 중 변수를 고정해 좁힌다.
- 전체 게이트 실패를 숨기기 위해 테스트를 skip하거나 타입·lint 규칙을 완화하지 않는다.
- 기존 실패가 있으면 이번 변경과의 관련성을 확인하고, 관련 없으면 명확히 보고한다.

## 완료 보고

- 재현 또는 완료 조건
- 확인한 원인과 근거
- 변경 파일과 회귀 테스트
- 실행한 명령과 결과
- 실행하지 못했거나 남은 위험
